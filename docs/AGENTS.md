# AGENTS.md — docs/

The GitHub Pages site, served from `main`, folder `docs/`: <https://durchgemacht.github.io/model27/>. Static files, no build step,
no framework. Read the root [`AGENTS.md`](../AGENTS.md) first.

```
index.html             home page (intro, mods, "what's new" from release.js)
flasher/index.html     the web flasher page
flasher/app.js         its UI: texts (English only), FEAT cards, GUIDE_OF, REF_MAINOS and REF_MODS (generated blocks), flashing steps
flasher/builder.js     builds the .syx in the browser (port of tools/build.py + mtlib); mainOsOf() gives composer.js
                       the user's MAIN OS
flasher/composer.js    composes the ticked machine cards in the browser (port of tools/compose.py without the
                       toolchain, notes/61): places the packages, fills the registrar's frame, computes the conflicts
flasher/flasher.js     .syx checks, Web MIDI sending: classic (CONFIG › UPGRADE) and fast (Transfer protocol, notes/37)
flasher/tweaks.js      GENERATED by tools/gen_flasher_tweaks.py — never edit by hand
manager/index.html     the manager (notes/77): one project per firmware, Switch backs up, flashes and brings back
```

## What the flasher shows

The main page (redesign of 2026-10-31, 1-bit look in `flasher/style.css`) offers the Model:Cycles and the fast method
only, on two screens: the cards, then the install steps (1 recalls the choice; 2 to 4 keep the numbers the texts refer
to). `SAMPLES_UI` in `app.js` (true on `flasher/?samples`, which the guide links) brings back the Official firmware and
Samples OS tabs and the machine picker; `CLASSIC_UI` (false) the classic method and Advanced. Those parts stay in the
page, hidden, and the smoke test still drives them. The cards sit in four sections by kind (`kindOf()`: added
machines, effects, Track FX, mods); only the exceptions carry a tag (Experimental), a card's Details say how it was
tested. Each section but Mods has a line under its title (`kind_<k>_sub` in `T`, the way in) and a How to use button
that opens one window over the page (`openInfo()`): `kind_<k>_info`, blocks of `[heading, text]` with what all the
section's cards share, and `kind_<k>_note`, an optional smaller note at the end. A card does not repeat its window.

## The manager

`manager/` (release 0.30, notes/77) keeps one project per firmware on the Model:Cycles: a firmware is a `.syx` the user
adds (any build, the official OS named by its hash in `KNOWN`), with its backups and its slot on the Cycles. Switch
runs five steps in a dialog: stop the sequencer, back up (request `0x6F`), flash (`upgradeFast` of `flasher.js`, the
user presses YES), bring the firmware's project back (checked by the settings the Cycles answers to `0x64`), save it in
its slot. It is not tied to the flasher: it only loads `flasher.js` and links nothing else. The library lives in the
browser's IndexedDB under the page's origin (an export from another address imports as is). `style.css` is the
flasher's 1-bit look, its own copy of the tokens, header, buttons and footer; class names that `site.css` styles too
(`.wrap`, `.top`, `.brand`, `.btn`, `.foot`) are overridden there, and the page's own classes avoid the others.
Light only, as the flasher. Checks: `tools/webmanager_check.sh` (the scripts on the host); the page itself against
the stand-in `tools/manager/fake-cycles.js` (serve the repository's root, load it by hand, `FakeCycles.install()`),
and on a Model:Cycles by the maintainer.

## English only

The whole site is in English (the maintainer's decision of 31/10/2026): no French, no `data-l` spans, no EN/FR
switch. `app.js` has one `T` and one `FEAT`; a `release.js` change is `{ en: "…" }`.
Write for musicians: what changes on the machine, which buttons to press, the limits; no addresses.

## Writing for users

Every text a user reads (cards, section windows, guide, home page, release notes) follows these rules, drawn from the
Model:Cycles and Syntakt manuals, Korg's monologue manual and teenage engineering's EP-133 guide (the maintainer's
decision of 04/11/2026). Existing texts are brought to them group by group: the Track FX cards, the effects, the
mods, the guide, the rest.

- **The reader** owns a Model:Cycles and knows its manual, not our code. They want to know what to press and what
  they will hear.
- **The manual's words**: preset (not sound), parameter lock, preset lock, LFO destination, Control All, MACHINES
  menu, PRESET menu, GRID RECORDING mode, signal path, recording. Never words from the code or the notes: record,
  slot, k 32, descriptor, id, neutral, real parameter, dearest, block, claim, take.
- **Keys and knobs.** A key in brackets in the source: `[RETRIG]`, `[TRIG] key`, `[FUNC] + [MACHINES]`; the page
  shows it as an inverted box, without the brackets. A knob or parameter in capitals: PITCH, SWEEP, LEVEL/DATA, DELAY
  TIME, VOLUME + DIST; the page underlines the names in `KNOBS` with dashes. Both by `rich()` in `flasher/app.js`
  (classes `key` and `knob`). Settings and machine names in capitals, unmarked: OFF, CHORD.
- **One action per sentence.** It starts with the verb and names every key, the held keys first, in the order the
  hands move: "In GRID RECORDING mode, press and hold a [TRIG] key and [RETRIG], then turn the knob." Never leave a
  key for the reader to fill in ("…, LFO to make them …").
- **Then what you hear or see**, in a sentence of its own. No filler ("as usual", "they work like the other
  knobs", "real parameters"). A range at the end, in brackets, only where it is not the usual 0–127: (-64–63).
- **Only what you need to start** on a card or in a window. Background, measurements and history go to the guide
  or the notes.
- **Structure.** A card: `short`, one sentence on what it does on the machine; the Details, the way in, then the
  controls. A section window and, as they are rewritten, the Details: blocks, each a short heading (the action or
  the parameter) and one or two sentences. In a card's Details, a block per knob: the heading the knob alone
  (SWEEP), then a whole sentence on what it sets, the term written out and the screen's abbreviation in brackets
  ("Sets the sample rate (RATE)."). A default goes into that sentence ("127, the default, is off"), not a block of
  its own. The name the screen shows starts the card's short text, without brackets: "CRU - Makes a track grainy …"
  (`screen` in `FEAT`, none where it is the card's name). `Note:` at the end, smaller, only for what protects the user's work. What all
  the cards of a section share lives in its window, not on each card.
- **Before showing a text**: every key combination checked against the code or the maintainer's test, every word as
  above, and each sentence one a Model:Cycles owner can follow without guessing a word.

## Adding a mod to the flasher

1. Add it to `FEATURES` in `tools/gen_flasher_tweaks.py` (`"status": "experimental"`, `cat`, `credit`, `license` when
   the mod carries outside code, `excludes`, `includes`, `needs` or `requires` if any), then
   `python3 tools/gen_flasher_tweaks.py` to regenerate `flasher/tweaks.js`. `cat` orders the card inside its
   section (machines, effects, mods: `kindOf()` in `app.js`), one of `CATS` (`pack`, `sound`, `seq`, `live`, `screen`,
   `io`); without it the card comes last in its section. The order of `FEATURES` is the build order (the `REF_MAINOS`
   keys); the page shows the cards by section, then `CATS`, then `FEATURES` order.
   `"requires": "<card id>"` is for an add-on that only works with another card (sample preview needs Model-TG):
   ticking it ticks that card too (with that card's own exclusions), unticking that card unticks it, its Details say
   "Works with …", and `ref_mainos.py` only lists combinations that hold both. Give the add-on the same `with` as the
   card it requires (sample preview takes `33-sample-preview-st` when Model-TG takes `30-model-tg-st`), and make the
   `requires` of each of its tweak files point at the matching tweak (`sample-preview` → `model-tg`,
   `sample-preview-st` → `model-tg-st`); `gen_flasher_tweaks.py` refuses a card that doesn't.
2. `python3 tools/check_overlaps.py`, then `python3 tools/ref_mainos.py --cycles … --syntakt …`: it rewrites `REF_MODS`
   (the hash of each tweak's writes and payload, checked by the page on every build) and `REF_MAINOS` (the whole MAIN
   OS of a sample: each mod alone, every pair, the largest combinations) in `flasher/app.js` (notes/49). A build whose
   mod or listed MAIN OS differs is refused; a combination outside the sample is built and checked mod by mod. The
   rules between mods (`excludes`, `includes`, a card's `requires`, `with`, the Syntakt engines' `tg` version) are read
   by `ref_mainos.py` as `app.js` reads them: a new kind of rule goes into both (`tools/webflash_smoke.js` ticks each card alone and every
   pair in the page and checks that each one is in the sample).
3. In `flasher/app.js`: the card texts in `FEAT`, as in *Writing for users*: `label`, the name alone (no "(effect)", no half sentence);
   `short`, one plain sentence on the card (about 80 characters, what it does on the machine); `desc`, the Details,
   a few short paragraphs separated by a blank line (`\n\n`): what it is, the buttons, the main limit, the rest in
   the guide; optional `note` (shown once ticked), only for what protects the user, one or two short sentences; `clash` if it
   has `excludes` (why it doesn't go with the other mod), `parts` for a pack (what it brings), a `short` per engine
   (`"eng-<code>"`) for an engine card. And the guide anchor in `GUIDE_OF` (one line per mod).
4. In `tools/webflash_smoke.js`: the expected order of tweaks, the expected **display** order of the rows (by
   section), and a check that its card and its guide link render.
5. A guide section in `guide/index.html` (next number, before *Samples OS*; renumber the ones after): a lede, the
   steps (`<ol>`) with the buttons in `<b>`, then `<dl class="facts">` with the limits and a *Tested* / *Experimental*
   line saying how it was checked. Copy the `#tempo` or `#trig-hold` section.
6. A new entry at the top of `assets/release.js`: next version (the top entry is the last), today's date, 2 to 4 changes
   (what the user gets, the limits, how it was checked, which mods it goes with). The home page shows it as is (the
   flasher only its version), so write it for musicians. Nothing posts it anywhere else: Modded-Cycles' Discord
   workflow went with `.github/` at the fork.
7. Bump the version stamp: the same `YYYY-MM-DD-NN` string in `window.MC_BUILD` (`flasher/index.html`) and every
   `?v=` of the four pages (`index.html`, `flasher/index.html`, `manager/index.html`, `guide/index.html`). A stale stamp
   makes browsers mix a new page with cached old scripts.

**An added machine** with a package (`tools/machines/<id>/manifest.json`, notes/59 to 61) is a machine card:
`"package": "<id>"` in `FEATURES` instead of `variants`, and no `excludes` by hand: `gen_flasher_tweaks.py` computes
them from the package's tweak alone (its generator writes it, with its `conflicts`) against the other cards offered,
and embeds the package and the registrar's frame. The page composes the ticked machine cards into one tweak, where
the first of them is, its id their packages' ids joined by `+`; `ref_mainos.py` composes each set of them with
`tools/compose.py`, one `REF_MODS` entry per set. Steps 2 to 7 above hold as for any card.

The home page list (`ol.mods` in `index.html`, each item with the controls it lights in `data-hl` and the screen
text in `data-lcd`) is a short selection, not every mod: add an item only when the mod is a headline one, and ask.

When the maintainer has tested it on their Model:Cycles: `status` to `"tested"` in `FEATURES` (regenerate
`tweaks.js`), the guide's *Tested* line, the release entry ("Tested on a Model:Cycles"), and the stamp again.

## Checks

```sh
python3 tools/gen_flasher_tweaks.py --check
tools/webbuild_check.sh        # builder.js == tools/build.py, byte for byte
tools/webcompose_check.sh [model-cycles_OS1.13.syx]   # composer.js == tools/compose.py (relocate.py), byte for
                                                      # byte; with the file, the composed tweaks and their MAIN OS
tools/webflash_check.sh        # flasher.js validates .syx like tools/mtlib/syx.py
tools/webflash_smoke.sh [model-cycles_OS1.13.syx model-samples_OS1.13.syx]   # the page in jsdom; with the real
                                                                         # files, the REF_MAINOS sample, each mod checked,
                                                                         # and the Model:Samples flows
tools/webmanager_check.sh      # the manager's scripts (tools/manager/*.test.js); BACKUP_SYX=, OS_SYX= add real files
```

`builder.js` and `tools/build.py` must stay equivalent: a change to how one reads a tweak goes into the other in the
same commit. The same holds for `composer.js` and `tools/compose.py` with `tools/relocate.py` (how a package is placed
and registered, notes/61); `tools/webcompose_check.sh` compares them. The flasher only offers tweaks that keep the OS update over USB working; `6ch-multiout`,
`sdvintage-snare` and `sdvintage-exact` stay command-line only.

The page must keep working from `file://` and under GitHub Pages: no `fetch` of local files (that is why `tweaks.js`
embeds the JSON), scripts loaded with relative paths. Users' files never leave the browser.
